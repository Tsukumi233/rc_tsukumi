# 通知系统设计

业务系统提交完整的 HTTP 请求，通知服务负责保存和异步投递。技术栈为 TypeScript、pnpm、Hono、BullMQ 和 Redis。

```text
业务系统 → Hono API → BullMQ / 持久化 Redis → Worker → 外部供应商
```

API 确认持久化后返回 202，不等待供应商响应。请求与投递状态保存在同一个 job 中，避免数据库与队列双写。

## 1. 系统边界

### 解决什么

接收、校验并持久化 HTTP 请求，提供入口幂等、异步投递、失败重试、Worker 崩溃恢复和状态查询。调用方只需构造请求，不必各自维护重试逻辑。服务同时限制调用权限、目标地址和请求大小。

### 不解决什么，为什么

| 不解决的问题                         | 原因与责任归属                                                                   |
| ------------------------------------ | -------------------------------------------------------------------------------- |
| 订单提交与通知提交的原子性           | 通知服务无法得知尚未提交给它的事件；需要业务系统自己的事务 Outbox 等可靠交接机制 |
| 供应商的业务幂等与业务结果           | HTTP 无法证明远端是否执行过；去重、业务错误解释和补偿由调用方或供应商负责        |
| 字段转换、签名、OAuth 刷新           | 本版接收构造好的请求，不承担各供应商的协议适配                                   |
| 严格顺序、工作流、逐次审计和管理后台 | 当前需求没有这些约束；先完成投递，出现具体需要再增加                             |

MVP 支持最多 64 KiB 的 UTF-8 文本 Body，不支持二进制上传或流式请求。

## 2. 可靠性与失败处理

### 投递语义

**有限重试、允许重复，不保证最终送达。** 默认最多消耗 12 个尝试额度，有效期 24 小时。任务可能多次送达，也可能在耗尽预算时仍未送达。

如果供应商已经执行，而 Worker 在保存结果前崩溃，恢复后可能重发。因此不能承诺 exactly-once；涉及扣库存等操作时，需要供应商支持业务幂等。外部 2xx 记为投递成功，不代表其业务处理完成。

受理可靠性依赖 Redis 的 AOF `always`、持久化卷和 `noeviction`。入口通过同一调用方的幂等键去重；入队确认丢失时，使用原 key 重试。Worker 的锁、续锁和崩溃恢复由 BullMQ 负责，失锁 Worker 的结果写回会被拒绝。单节点仍不能抵抗磁盘永久损坏。

### 失败或长期不可用时怎么办

| 情况                                                       | 处理                                                     |
| ---------------------------------------------------------- | -------------------------------------------------------- |
| 2xx                                                        | 标记 succeeded                                           |
| 网络错误、超时、408、429、5xx                              | 指数退避并加随机抖动；遵守 Retry-After，受次数和期限限制 |
| 其他 HTTP 状态、非法目标、DNS ENOTFOUND、明确 TLS 验证错误 | 标记 dead，停止自动投递；3xx 不跟随跳转                  |
| 预算耗尽或过期                                             | 标记 dead，保留最后错误，供人工排查                      |

供应商长期不可用、预算耗尽后停止自动重试，避免持续制造无效请求。修复后可用新的入口 key 创建一轮投递；供应商的业务幂等键应保持不变。MVP 没有自动批量重放和告警平台。

过期检查在 Worker 执行前进行；Worker 全部停止时，任务不会立即变成 dead，恢复消费后才处理。已开始的 HTTP 在期限后返回 2xx，仍记录成功。

## 3. 取舍与演进

### 哪些 AI 建议没有采纳

AI 初版建议用 PostgreSQL 自写任务领取、租约回收和轮询，以减少中间件。我没有采纳继续维护这套实现的建议：这些是通用队列能力，自研会增加代码和故障处理负担。

最终采用 BullMQ。它能覆盖延迟重试、并发消费和崩溃恢复，投递代码保留 HTTP 策略，调度交给库。选型依据是需求覆盖、自有代码量、维护成本和实际性能；社区维护不能代替集成测试。

本版也没有引入工作流引擎、独立 cron 服务或额外的 PostgreSQL 状态库：当前没有流程编排和周期任务需求，第二份状态库还会增加一致性处理。这些是未采用的备选方案，不都属于我实际否决过的 AI 建议。

如果已有 PostgreSQL 业务事务需要一起提交任务，pg-boss 是值得优先评估的替代方案。当前服务没有这项需求，BullMQ 的锁令牌和 HTTP 重试扩展更便于接入。详细验证见 [VALIDATION.md](VALIDATION.md)。

### 流量或复杂度增长后怎么改

| 出现的问题                     | 下一步                                                                 |
| ------------------------------ | ---------------------------------------------------------------------- |
| HTTP 等待导致积压              | 提高 Worker 并发或增加实例；先确认供应商能承受的请求量                 |
| 供应商限流或故障相互影响       | 按供应商拆队列，使用库的限流能力                                       |
| 历史任务占满内存               | 定义保留期和幂等窗口，先归档终态，再清理 job；新增存储时处理交接一致性 |
| Redis 成为瓶颈或需要更高可用性 | 用实际负载测试，再评估分区、故障转移或其他队列存储                     |
| 签名、OAuth、业务响应差异增多  | 增加供应商适配层                                                       |

当前终态任务不自动删除，以保留查询和入口幂等，代价是内存与磁盘持续增长。演进依据是积压、错误率、资源占用和新增业务约束，不预设达到某个 QPS 就更换架构。

接口不变量、锁与重试细节见 [IMPLEMENTATION.md](IMPLEMENTATION.md)；AI 分工见 [AI_USAGE.md](../AI_USAGE.md)。
