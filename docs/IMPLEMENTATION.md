# 实现细节

设计选择与系统边界见 [DESIGN.md](DESIGN.md)。本页记录接口契约、故障窗口和部署条件。

## API 契约

`POST /v1/notifications` 使用内部 Bearer Token 识别调用方；必须提供入口 `Idempotency-Key`。Body 包含 `url`、`method`、`headers`、可选原始文本 `body`。Hono 负责路由，Zod schema 负责校验并生成 OpenAPI；Hono 本身不凭空生成业务实现。

| 返回            | 含义                                                          |
| --------------- | ------------------------------------------------------------- |
| 202             | 本次首次入队，持久化操作已确认；不代表外部已收到              |
| 200             | 同一调用方、同一 key、同一快照已存在，返回原通知              |
| 409             | 同一调用方的 key 被用于不同快照                               |
| 400 / 403 / 413 | 输入非法、目标未授权、请求过大                                |
| 503 / 请求超时  | 没有取得可靠确认；可能尚未入队，也可能已入队。使用原 key 重试 |

`GET /v1/notifications/{id}` 只允许所属调用方查询；不存在或不属于自己均返回 404。返回状态、尝试预算、时间和最后错误摘要，不返回目标凭证或 Body。

入口遵守以下约束：

1. **受理与入队是同一份记录。** 一个 BullMQ job 保存不可变请求快照和所有调度信息，避免“通知记录写成功但队列没写”的双写窗口。
2. **同一调用方/key 最多创建一份存活任务。** 由 caller/key 确定 UUID 格式 job ID，利用 BullMQ 的原子入队脚本去重；回读实际存储的内容做 hash 冲突检查。每次调用的随机 acceptance 标识用于区分首次受理和重放。
3. **幂等不依赖进程内存。** API 重启、确认丢失和并发调用仍读取相同 job。成功、失败任务均不自动删除，因此入口 key 不会随执行结束而失效。
4. **重试不重构业务请求。** Header 名称归一化；Body 字节内容和 query 顺序不改变。调用方显式传入供应商支持的幂等 Header，入口 key 不会擅自注入外部请求。
5. **外部调用不进入存储事务。** 网络等待由 Worker 承担，受理接口不等待供应商。

job ID 使用 SHA-256 的 122 个有效位；哈希碰撞概率极低，但不是数学上的零。回读还检查 caller/key/hash，发生碰撞时返回冲突，不覆盖已有请求。

## 存储与 Worker

### 唯一状态来源

没有业务状态表与队列状态表之间的同步。查询通过 BullMQ 的公开 API 读取任务并映射：

| BullMQ 状态       | 业务状态  |
| ----------------- | --------- |
| waiting / delayed | pending   |
| active            | in_flight |
| completed         | succeeded |
| failed            | dead      |

查询由多次读取组成，是观察性接口，并非强一致事务快照。并发执行时可能短暂读到稍早的状态；观察到终态后会刷新结果字段。MVP 不提供删除、重放同一个 job、外部修改队列内部键等操作。

Worker 返回成功结果时，由 BullMQ 校验锁令牌并提交 completed 和返回值。抛出普通错误时由库安排重试；抛出 UnrecoverableError 时直接终止。不存在应用先更新“成功表”、随后另行 ACK 的步骤。

### 崩溃窗口

| 中断点                           | 行为                                                      |
| -------------------------------- | --------------------------------------------------------- |
| 入队前失败                       | 返回失败，调用方原 key 重试                               |
| 入队成功、确认或 API 响应丢失    | 原 key 重试读取已存 job，不重复创建                       |
| Worker 取得任务、HTTP 前崩溃     | 库在锁过期和 stalled 检查后重新调度                       |
| 供应商已执行、结果尚未提交时崩溃 | 可能再次投递；供应商需要幂等                              |
| 旧 Worker 失锁后恢复并写结果     | 库的令牌校验拒绝过期写回；不会覆盖新 Worker 的结果        |
| Redis 暂不可用                   | API 快速失败；Worker 连接恢复后继续，由库处理任务锁和恢复 |

锁无法阻止已经发出去的 HTTP 请求继续在远端执行。供应商仍可能收到重复请求。本项目测试实际验证了过期令牌写回被拒绝。

默认 HTTP 总超时 10 秒、锁期限 30 秒、stalled 扫描间隔 30 秒。正常运行由 BullMQ 续锁。进程崩溃后的恢复需要等待锁过期及扫描轮次，不承诺精确 30 秒恢复。生产时需监控 stalled 事件和事件循环阻塞。

### 持久化受理的条件

Redis 保存任务，必须启用以下配置：

```conf
appendonly yes
appendfsync always
no-appendfsync-on-rewrite no
maxmemory-policy noeviction
```

Redis 官方说明 `always` 在向客户端回复前完成该批次 AOF fsync。因此服务在上述配置成立、写入成功并回读 job 后才确认受理。`everysec` 有约一秒的数据丢失窗口，不符合本项目选定的受理承诺。启动和 `/readyz` 会核对相关配置及 AOF 写入状态；Redis ACL 需允许对应的只读 CONFIG GET / INFO。配置变更属于运维动作，不能绕过这项约束。[Redis 持久化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

Compose 使用持久化卷和 256 MiB 内存上限；达到上限时拒绝写入而不淘汰旧任务。AOF always 增加磁盘写入成本，性能测试必须使用同样配置。可选 msgpackr 原生扩展未启用，使用依赖提供的 JavaScript 实现。

单节点仍不能抵抗磁盘永久损坏、管理员删除数据卷或所有副本同时丢失。未来高可用方案需要另外定义故障转移的 RPO；不能把异步复制当成绝对不丢。服务器需要时间同步，TTL 和重试时间使用应用时钟。

## 重试计数与期限

默认最多 12 个尝试额度，期限 24 小时。BullMQ 的 `attemptsStarted` 用于约束包含崩溃在内的处理次数；超过额度时 Worker 不再发 HTTP。库可能额外激活一次任务来将其终止；API 的 attemptCount 表示已消耗额度，上限为 maxAttempts，并不是供应商实际收到的请求计数。

使用 BullMQ 提供的指数退避和 jitter，再将普通退避限制到 1 小时。有效的 Retry-After 不受这个上限截短；取两者中更晚的时间。重试时间达到期限则直接终止。延迟唤醒、续锁、恢复由库完成，应用没有自行维护计时器队列。

任务每次执行前检查期限；已经开始的 HTTP 若在期限后收到 2xx，仍记录成功。Worker 全部停止时，不会另起一个自写扫描器立即把过期任务改成 dead；恢复消费后先检查期限，过期任务不会发送。期限表示禁止开始新投递的边界，不是精确的终态更新时间承诺。

供应商长期不可用会形成可见的失败任务。先排查目标、凭证和服务状态，再使用新的入口 key 创建新的有限投递周期；如果供应商支持业务幂等，保持它的业务幂等键。MVP 不自动批量重放失败任务。

## 访问限制

精确 origin 白名单和连接时 DNS 检查用于约束外部访问；不跟随重定向，不信任传入 Host 等逐跳 Header。生产仅允许 HTTPS 公网目标；本地 mock 的私网开关仅能在 development/test 打开。日志与查询不泄露请求凭证。生产部署还应使用 Redis ACL/TLS、私有网络及受保护的数据卷；示例配置只用于本机演示。

## 旧原型切换

本次是笔试 MVP 的存储替换，不是对已上线服务的无停机迁移。旧 PostgreSQL 数据卷没有删除，也没有自动导入 Redis。若旧原型有需要保留的任务，应先停止受理、处理或导出剩余任务并核对终态，再切换；不允许启动两套 Worker 对同一批业务盲目重放。旧通知 ID 不会自动出现在新服务中。
