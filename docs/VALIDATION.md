# 验证记录

验证日期：2026-09-13。环境：macOS ARM64、Node.js 24.21.0、pnpm 10.34.5；Docker Redis 8.10.1，BullMQ 6.3.4，ioredis 6.0.0。依赖解析版本保存在 pnpm-lock.yaml。

## 自动检查

```sh
pnpm check
pnpm format:check
```

实际通过 **3 个测试文件、34 项测试**，类型检查和生产构建通过。测试约 4.7 秒，不包括安装和镜像构建。Redis 是真实服务，各测试套件使用独立随机队列；不使用内存队列替代锁、延迟任务和 stalled 恢复。

| 范围         | 已覆盖场景                                                                                                                                                              |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API          | 持久化后 202；12 个并发相同 key 只创建一个 job；内容冲突；跨调用方隔离；失败前不确认；确认丢失后原 key 重放；不可用存储快速失败；AOF 写失败就绪检查；OpenAPI 与输入限制 |
| HTTP         | 请求快照；503 后恢复；400 终止；302 不跳转；网络超时；收到 2xx 头后不等待无限 Body；429 的 Retry-After                                                                  |
| 生命周期     | 期限前禁止过期任务发送；Retry-After 超过期限直接终止；成功后入口重放不重置任务；最后一个额度被崩溃消耗后不多发 HTTP                                                     |
| Worker       | 两个 Worker 并发领取同一队列；实际 HTTP 并发不超过配置总量；旧令牌写回被库拒绝；HTTP 前/后两处真实 SIGKILL 恢复                                                         |
| 安全与规范化 | 私有 IPv4/IPv6 与映射地址；DNS 全地址检查及实际连接拦截；精确 origin；Header 规范化；Body/query 顺序保留；非法配置                                                      |

确认丢失通过“真实入队成功后让调用包装层抛错”注入，验证 503 后重试读取同一 job；不声称模拟了所有网络断连时序。AOF 写失败的就绪测试通过替换 INFO 返回值注入，不是实际填满磁盘。

Worker 崩溃测试启动真实子进程，到达约定位置后 SIGKILL。使用 500 ms 锁和 100 ms stalled 检查缩短等待，实际等待库的恢复，不直接修改 Redis 锁。过期令牌测试用库公开的手动领取接口和短锁，接管完成后尝试旧令牌提交，验证库拒绝操作。

SQL 行锁、双表事务和迁移器测试随旧实现移除，改为验证当前的队列契约；测试数量变化不代表保留了原来所有内部实现测试。MVP 不再提供逐次 attempts 账本。

## 行为级 E2E

```sh
pnpm test:e2e
```

本地实际通过 **16 项 E2E**，用时 34.52 秒，包含容器构建、启动和清理。与原有 34 项单元/集成测试分别运行，共 50 项通过。

测试启动独立的 Docker API、Worker、Redis 和模拟供应商。测试代码不导入应用、队列或 Redis 实现，只通过 HTTP 提交、查询，并检查供应商记录的请求、接收时间和业务执行次数。

| 可观察行为        | 断言                                                                          |
| ----------------- | ----------------------------------------------------------------------------- |
| Worker 停止时受理 | 返回 202，供应商尚未收到请求；启动后原 Header 和 Body 被送达                  |
| 入口幂等与隔离    | 12 个并发相同请求只触发一次投递；内容冲突返回 409；不同调用方不能读取彼此任务 |
| 输入限制          | 未授权、非法 Header、超大 Body、未许可目标被拒绝，未向供应商发送对应请求      |
| 失败重试          | 两次 503 后第三次成功；持续 503 和超时在 3 个尝试额度后终止                   |
| Retry-After       | 供应商两次收件至少间隔 1 秒；等待时间超过期限时直接 dead                      |
| 不可重试响应      | 400 和 302 各只发送一次，未跳转                                               |
| 响应丢失          | 供应商收到两次请求，业务执行一次                                              |
| 并发上限          | 6 条慢请求在供应商侧观测到的并发峰值为 2                                      |
| API 重启          | 已受理任务和入口 key 保留，恢复后只投递一次                                   |
| Worker SIGKILL    | 在供应商执行、尚未返回响应时杀进程；恢复后重发，业务仍只执行一次              |
| Redis SIGKILL     | 停机时入口返回 503；重启后原 202 任务和幂等记录保留，继续投递成功             |

测试配置为 HTTP 超时 3 秒、锁期限 5 秒、stalled 检查间隔 500 ms、最多 3 个尝试额度、有效期 60 秒，缩短故障测试等待。Redis 仍使用 AOF always 和 noeviction。每轮用随机容器项目、端口和专用数据卷，结束后删除测试容器和数据卷，不操作演示栈。

首轮发现测试仍使用 API 重启前的随机端口，导致恢复检查失败；根据容器日志确认 API 已启动后，改为重启后重新发现端口。修正后 16 项通过，没有将这一测试环境问题记成业务代码缺陷。

报告为 `artifacts/e2e/results.json`，容器日志为 `artifacts/e2e/compose.log`。CI 已配置执行和上传这些文件；尚未执行远端 CI。

E2E 中只有外部供应商由测试服务模拟，故障通过真实容器操作注入。供应商的去重行为由这个模拟服务实现，不能据此断言其他供应商支持幂等。未覆盖断电、磁盘损坏、HA 切换或所有网络分区；“不再重试”的断言还包括终态后的短时间观察，不是无限时间证明。

## Redis 持久化故障验证

实际执行：

```sh
pnpm exec tsx scripts/check-restart.ts
```

流程：停止 Worker → 创建任务并收到 202 → 确认 pending → SIGKILL Redis → 使用原数据卷启动 Redis → 确认原 job 仍存在 → 原 key 重放返回 200 和相同 ID → 启动 Worker → succeeded。

结果通过，记录 ID 为 `ffe7e903-840e-8042-a4ab-c817d06970de`。验证使用 AOF always、noeviction 和持久化卷。它证明了这次容器进程被杀后的恢复，不等于完成了断电、文件系统损坏、磁盘写满、主从切换或跨机房容灾验证。

## 相同请求工作负载的比较

实际执行 `pnpm benchmark`，相同机器、Docker API/Worker、同一模拟供应商实现，100 条每条 1 KiB 的 POST，入口并发 10，单个 Worker 并发 10。客户端每 100 ms 轮询尚未完成任务的状态。新 Redis 保持 AOF always，未为了测试放松持久化。

| 测量                         | 自写 PostgreSQL 原型 | BullMQ + Redis |
| ---------------------------- | -------------------- | -------------- |
| 100 条全部受理               | 161 ms               | 164 ms         |
| 从开始受理到整批观测完成     | 10,399 ms            | 192 ms         |
| 整批完成吞吐                 | 10 条/秒             | 520 条/秒      |
| 受理延迟 p95                 | 89 ms                | 49 ms          |
| 客户端观察的投递完成延迟 p95 | 10,243 ms            | 167 ms         |

这是一次本地对比样本，包含网络、鉴权、存储、真实 HTTP 及客户端观测成本，不是队列库的纯吞吐测试。完成延迟受查询节奏影响，样本没有长期预热和重复统计，因此不应解释为稳定的 p95 或生产 SLA。

旧 Worker 每秒轮询一次，每轮最多领取 10 条，即使 HTTP 很快也被这个配置限制。BullMQ 持续消费消除了该瓶颈。这项结果支持当前替换后性能没有退化；不能推出“Redis 天生比 PostgreSQL 快 52 倍”。没有对 pg-boss 做压测，也没有声称旧方案已调优至极限。

基准会保留生成的任务；默认仅调用本地 mock。改变目标或请求数量前应检查环境与资源预算。
